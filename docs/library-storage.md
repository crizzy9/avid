# Local library storage

The shared repository uses an explicit storage port. `DexieLibraryStorage` retains the existing IndexedDB database and its version 3 tables. `NativeLibraryStorage` speaks the typed native bridge in `packages/core/src/storageProtocol.ts`. The hook accepts `useLibrary({storage})`; the selected backend stays fixed for that mounted library. A failed native operation is surfaced to the caller rather than silently switching databases.

Every repository instance remains bound to the normalized server URL and authenticated user ID. Ordinary offline and demo storage does not depend on a live authentication token. Tokens, cookies and passwords do not belong in these tables. Rows retain the existing `key = JSON.stringify([scope, id])` identity; outbox `entityKey` is a secondary filter.

## Atomicity

Repository writes, conflict resolution, preference patches, and native journal replay use an explicit transaction-scoped repository object. There is no mutable global transaction owner. The IndexedDB adapter runs those operations in a native Dexie transaction; the native adapter records reads and buffered mutations, then asks SQLite to compare every observed table revision and commit all mutations atomically. A conflict replays only the local callback, with at most 16 attempts. Callbacks must never send network requests or perform other external effects.

Revisions belong to an account and table and survive account clearing, preventing old snapshots from becoming valid again. Empty commits validate read snapshots. Entity claims, exact checkpoint timestamps, immutable activity IDs, note ID remapping, deletion tombstones, native replay fingerprints and read-only provenance retain the same repository rules. Checkpoint reads request exact book IDs, rather than loading the entire catalog.

## Imported files

The bridge transfers file data in decoded chunks of at most 256 KiB. A staging upload has an account scope, exact size, MIME type and name; appends require the next offset. Completion yields an immutable scoped blob reference, which is published together with local edition metadata by the atomic commit. Native storage must validate the reference's ownership and metadata. Interrupted or unreferenced staging data is eligible for native cleanup.

Imported-book listing requests only file identities; it does not read file bodies. An explicit file open reads bounded chunks and verifies length and end-of-file before constructing the browser File. That browser representation can still require memory proportional to the opened file; the separate native audio receipt/player path is used for large native audio sources. The storage protocol does not imply that a WebView can render a 4 GiB ebook.

## iOS repository backend

`AvidLibraryStorage.swift` implements all nine tables in a private SQLite WAL database with full synchronous commits, indexed scoped identities, entity filters and monotonic table revisions. `AvidLibraryStoragePlugin` exposes `read`, `commit`, `beginBlob`, `appendBlob`, `finishBlob`, `readBlob` and `cancelBlob` to the main Capacitor host. Calls run on a serial worker; widgets do not receive this repository bridge. Metadata access uses the explicit local partition and does not require an active network session, so a final checkpoint for an old account can still be saved safely.

Private file transfers use exact sequential chunks of at most 256 KiB, 4 GiB per file, an 8 GiB reservation quota, at most four pending transfers and 4,096 receipts. JSON rows and transactions are limited to 8 MiB and 64 MiB; snapshots and mutations are limited to 100,000 rows. Query IDs are batched beneath conservative SQLite parameter limits. Binary paths are generated opaque UUIDs; callers cannot provide a filesystem path. Files use iOS protection until first unlock, are excluded from backup through the private directory, and are published only after their size and immutable receipt match the account transaction. Unreferenced staging expires after one hour; a successful read extends the grace period, and referenced files are retained.

Pending handles bind the process and native connection epoch. Logout or a different-account adoption invalidates them, while same-account token renewal preserves them. The epoch lock prevents a queued append or finish from crossing the account-change barrier. Completed references remain account-scoped and readable after a new connection; metadata partitions are not treated as network authorization.

Fifteen standalone native tests compile the production Foundation/SQLite implementation and exercise real files and SQLite, including reopening, CAS, multi-table rollback, ordered clearing, byte-exact Unicode identities, filtered queries, exact multi-chunk files, partial/wrong-scope requests, epoch/process invalidation, receipt corruption, quotas, expiration/read grace, symlinks, and schema/size validation. The suite passes locally with Swift 5.10.1, Foundation and SQLite on Linux, and all 15 tests passed on macOS in CI at `63f8d8f`. Run the same source on macOS with:

```sh
swiftc apps/mobile/native/ios/AvidLibraryStorage.swift apps/mobile/native/ios/tests/LibraryStorageTests.swift -o /tmp/avid-library-tests
/tmp/avid-library-tests
```

These tests exercise the real backend. The Capacitor wrapper also compiled as part of the unsigned iOS app/widget and opt-in CarPlay builds at `63f8d8f`. Installed bridge calls, iOS data-protection behavior while locked, signing and physical-device recovery remain separate acceptance gates.

## Android repository backend

`LibraryStorageStore.kt` implements the same nine-table protocol in a private SQLite WAL database with full synchronous commits and schema version 1. `AvidLibraryStoragePlugin` exposes the seven bridge methods on a serial worker. Every metadata transaction uses the explicit canonical account partition, validates all expected table revisions before applying ordered mutations, and preserves revisions after clearing. Exact-ID reads use batches of 400 within one snapshot. Large JSON records are read directly through a prepared statement, avoiding Android's smaller CursorWindow row limit; identity-only reads do not load record payloads or file bodies.

Binary receipts and metadata live below Android's private `noBackupFilesDir`, with directory/file permissions of 0700/0600. The limits match iOS: 256 KiB chunks, 4 GiB per file, 8 GiB reserved in total, four pending transfers, 4,096 receipts, and one-hour cleanup for unused staging. Rows and batches are bounded at 8 MiB and 64 MiB. Files are synced before their completed receipt is published, and local-file commits validate the exact scope, size, MIME type and name. A binary operation captures the native connection epoch before entering the worker queue and checks it under the session-store lock when executing. Logout or account adoption invalidates pending handles; same-account token rotation preserves them. Existing metadata partitions and completed references remain independently scoped.

Sixteen tests pass against Robolectric 4.16.1's native AOSP SQLite runtime at Android API 28, using real temporary database and file paths. They cover durable reopening and schema rejection, multi-table CAS and SQL-trigger rollback, ordered mutations and revision preservation, separate database connections, filtered outbox/session/receipt queries, JSON larger than CursorWindow, 1,001-ID batches, exact file chunks and EOF, corrupt or wrong-scope receipts, epoch/process invalidation, sparse 4 GiB offsets, quotas, expiration, private permissions and symlinks. A test-only `LibraryFileOs` adapter maps six Android filesystem methods to the host's real Unix attributes, permissions and file-channel sync because Robolectric's default filesystem shadow reports synthetic missing-file attributes. SQLite is not replaced by a protocol fixture or mock database.

The integrated local Android run passed all 62 tests with zero skipped cases. CI at `63f8d8f` also passed the Android unit-test task and compiled both default and Auto-enabled debug APKs, including the Capacitor repository wrapper. From `apps/mobile/android`, run `./gradlew :app:testDebugUnitTest :app:assembleDebug` with a configured Android SDK and writable test home. This evidence does not qualify installed Capacitor calls, Android filesystem behavior across power loss, low-storage failures, or restart/kill behavior on physical devices. Those remain device acceptance gates; API 24–27 compatibility paths also need device qualification.

## Copy before native activation

`migrateLibraryAccount({source, target, session, isActive?})` in `packages/core/src/storageMigration.ts` copies one account. It reads a consistent legacy snapshot, compares existing destination rows, and atomically adds only missing rows. A different row with the same identity stops the copy; unrelated destination rows remain intact. File fingerprints include name/type/size and SHA-256 hashes of 256 KiB chunks. Object fingerprints use deterministic key ordering, preserving array order and rejecting values that cannot be represented safely.

A second transaction verifies the persisted destination against that snapshot and creates a completion receipt only after successful read-back. Destination changes during verification invalidate the CAS and force another comparison. The source is checked again after copying; a detected change prevents completion. Bootstrap must keep the legacy account inactive while copying: this is not a distributed transaction across two independently writable databases. Source records, files, queues, and receipts are never deleted or changed by migration. A failure after the first copy is safe to retry; a conflict remains visible and requires a deliberate choice outside this helper.

For automatic readiness, construct `new MigratingLibraryStorage(source, target)` and pass that stable instance to `useLibrary({storage})`. Its `read` and `atomic` methods wait for one shared migration promise per canonical account scope. `.ready(scope)` exposes the same promise for bootstrap status. Failed attempts reject all waiters and release the failed cache entry so a later operation can retry. Successful readiness is cached; a validated completion receipt also makes later process starts idempotent. Native data is then authoritative: later edits in the preserved legacy database are intentionally not imported automatically, and legacy files are not rehashed on every activation.

Thirteen migration/readiness tests cover every table, exact file bytes, same-size corruption, conflicts, missing persisted rows, failure between copy and receipt, source changes, concurrent destination edits, cancellation, malformed receipts, account isolation, one readiness flight for concurrent reads/writes, visible failures and retries. Verification of native local files currently reconstructs one browser Blob at a time; transport and hashing use bounded chunks, but verification memory can still grow with that file's size. This is separate from the streaming native audio receipt path. The actual SQLite evidence is recorded above; installed-platform restart/kill and recovery qualification remain separate gates.
